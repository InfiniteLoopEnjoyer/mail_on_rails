# Security Audit Report: mail_on_rails

This is a security review of the full codebase, with emphasis on SMTP/IMAP hardening and data-leak paths. No code was changed.

**Updated 2026-08-07:** resolved findings have been removed from this document (see git history for the original audit): vacation responder backscatter, outbound TLS verification (DANE + MTA-STS client enforcement), the IMAP accept-side gaps (per-IP connection cap, rate limit, auth lockout — now shared `netserv` scaffolding with SMTP), IMAP fail-open TLS boot, the terminal `unscanned` scan state (hourly `RescanUnscannedMessagesJob`), and SCRAM iterations at the RFC floor (now 100k). The published MTA-STS mode is now configurable but production still runs `testing` — flipping to `enforce` remains an open ops action below.

---

## Executive Summary

The project shows strong security engineering overall: TLS 1.2+ with AEAD ciphers, mandatory encryption before credentials on both protocols, layered auth throttling and per-IP accept-side abuse controls on both SMTP and IMAP, anti-abuse limits on submission, cross-account isolation tests, HTML mail sandboxing, parameterized SQL, and removal of the old internal HTTP API.

The largest remaining **architectural** gap is **no RBAC** — every signed-in web user is a full admin. The largest **operational** gap is that database backups are unencrypted and stay on the same volume as the database.

## Open Findings

### 1. No authorization model on the web UI (full admin for any session)

**Location:** All authenticated controllers; notably `app/controllers/emails_controller.rb`, `app/controllers/email_accounts_controller.rb`, `app/controllers/domains_controller.rb`, `app/controllers/users_controller.rb`

**Issue:** Any authenticated `User` can:
- Read/send as **any** `EmailAccount`
- Create/delete domains and publish DNS to Cloudflare
- Manage users and reset passwords
- View all mail, exports, audit data, live connections

**Impact:** A single compromised web session (phishing, stolen laptop, weak password without 2FA) compromises the entire mail system. This is documented as intentional for single-operator use but is a serious risk if multiple people share access. Tracked in the README roadmap.

---

### 2. Database backups contain full mail and secrets metadata

**Location:** `app/jobs/database_backup_job.rb`, `docs/backups.md`

**Issue:** Nightly `pg_dump` includes:
- All RFC822 message bodies (`email_messages.raw`)
- Password digests, encrypted SCRAM/TOTP/DKIM material
- Session and audit data

Backups live on the **same persistent volume** as the app; offsite copy is manual.

**Impact:** Disk compromise, backup theft, or a volume snapshot leak exposes the entire mailstore. No at-rest encryption of backup files is implemented.

---

### 3. Metrics endpoint exposure surface

**Location:** `app/controllers/metrics_controller.rb`, `config/routes.rb`

Bearer `METRICS_TOKEN` gating is implemented correctly (`secure_compare`, 404 when unset). However:
- No network ACL in the app (documented — relies on firewall/VPN)
- Exposes aggregate counts: accounts, messages, storage bytes, auth failure tallies, live connection counts

**Impact:** Token leak gives operational intelligence useful for targeted attacks. Not a direct data leak of message content.

---

### 4. Authenticated spam paths fail open when rspamd is down (by design)

**Locations:** `lib/mail_on_rails/smtp_server.rb` (`submission_spam_verdict`), `app/models/composed_email.rb`

Authenticated submission (SMTP and web composer) **allows** mail when rspamd is unavailable. ClamAV on inbound is fail-closed (451); rspamd on outbound is fail-open by documented design (spam scoring is advisory; blocking every send on a scorer outage punishes the user, not the bot).

**Impact:** A compromised account + rspamd outage = unrestricted spam from your IP. Accepted residual risk; noted here so the tradeoff stays visible.

---

### 5. Cloudflare API token scope

**Location:** `app/models/cloudflare_dns.rb`, `.kamal/secrets-common`

Token needs `Zone:Read` + `DNS:Edit`. A leaked token enables DNS hijack (MX, SPF, DKIM TXT), which is catastrophic for a mail host.

**Mitigation in code:** `DnsPublisher` is conservative (won't overwrite existing MX/SPF/DMARC). **Mitigation in ops:** token should be zone-scoped and rotated.

---

### 6. Development seeds use trivial passwords

**Location:** `db/seeds.rb`

`password123` for admin and mail accounts in **development only**. Safe if `Rails.env.development?` is always true when seeds run; dangerous if seeds are ever run elsewhere.

---

### 7. Audit and auth-attempt logs retain identifying data indefinitely

**Locations:** `app/models/audit_event.rb`, `app/models/auth_attempt.rb`

- Audit events: never pruned by documented design ("an audit trail with a retention window is a suggestion, not a record"); store `user_email`, `ip`, JSON `details`
- Auth attempts: usernames and IPs retained (30-day default retention, pruned daily); **passwords explicitly never stored** (well documented)

**Impact:** DB breach exposes who tried to log in and what admins did. Not a live credential leak, but a privacy/forensics liability.

---

### 8. CSP `style-src 'unsafe-inline'` (required for mail rendering)

**Location:** `config/initializers/content_security_policy.rb`, `app/views/email_messages/show.html.slim`

Email HTML renders in a **sandboxed iframe** (`sandbox="allow-popups allow-popups-to-escape-sandbox"`) with Loofah-based sanitization. CSP allows inline styles for newsletter compatibility.

**Impact:** If the sanitizer misses something, impact is contained to the iframe (no scripts, opaque origin). Residual risk is phishing styling / deceptive links (partially mitigated by `EmailHtmlSanitizer#expose_deceptive_links`).

---

### 9. SCRAM without channel binding

**Location:** `lib/mail_on_rails/imap/scram.rb`, IMAP `authenticate_scram`

SCRAM-SHA-256 is implemented correctly (`valid_proof?` uses `fixed_length_secure_compare`), but channel binding (`tls-server-end-point`) is rejected. A stolen SCRAM proof could theoretically be replayed on another TLS session to the same server (narrow scenario).

## Low Severity / Informational

| Area | Assessment |
|------|------------|
| **Password storage** | bcrypt for `User` and `EmailAccount`; SCRAM verifier keys encrypted at rest |
| **Web session** | Signed `httponly` `same_site: :lax` cookie; `reset_session` on login; idle timeout (default 24h) |
| **2FA** | TOTP + WebAuthn; pending 2FA state in encrypted session with 5-minute deadline; rate limited |
| **Password reset** | No user enumeration; rate limited; token invalidates on password change |
| **CSRF** | Enabled everywhere except `/metrics` (bearer-only, intentional) |
| **SQL injection** | ActiveRecord parameterized queries; FTS uses bound `?` parameters |
| **Internal API** | Retired; routes return 404 (`config/routes.rb`, integration tests) |
| **Action Mailbox ingress** | Hard-pinned to 404 |
| **SMTP smuggling** | CRLF handling, dot-stuffing, size caps, line limits |
| **STARTTLS injection (IMAP)** | Pre-TLS buffer discarded on upgrade (CVE-2011-0411 class) |
| **Header injection** | `Store::SmtpBackend#sanitize_header` strips CR/LF; trusted headers stripped from DATA |
| **Cross-account IMAP isolation** | Extensively tested (`test/vendored/imap/cross_account_isolation_test.rb`) |
| **Re-auth on IMAP** | Second LOGIN/AUTHENTICATE rejected after authentication |
| **SASL authzid** | Ignored; session bound to authcid only |
| **Generated passwords** | `SecureRandom.base58(36)` — strong |
| **Logging** | `filter_parameter_logging` covers passwords, tokens, OTP, etc.; SMTP AUTH redacted in trace mode |
| **Docker** | Non-root `rails` user (uid 1000) |
| **CI** | Brakeman, bundler-audit, importmap audit, Trivy |
| **Secrets in repo** | No committed `.env`; `master.key` gitignored; credentials encrypted |
| **Host header** | `config.hosts` set from `MAIL_ON_RAILS_WEB_HOST` in production |
| **ReDoS** | Global `Regexp.timeout` (default 3s) |

## Accept-Side Posture (SMTP and IMAP)

Both protocol servers share the `lib/mail_on_rails/netserv` listener scaffolding:

- AUTH/LOGIN only offered over an encrypted channel (SMTP `auth_offered?`; IMAP `LOGINDISABLED` / `[PRIVACYREQUIRED]`)
- TLS 1.2+, AEAD ciphers only; cert hot-reload on mtime change; explicit cert config fails closed at boot on both protocols
- Per-IP concurrent-connection cap, sliding-window connection-rate tarpit, and pre-greeting auth lockout on both protocols (`SMTP_*` / `MAIL_ON_RAILS_IMAP_*` env knobs)
- Admin IP/CIDR denylist enforced before any banner on both protocols
- ClamAV fail-closed on inbound SMTP DATA (550 infected, 451 scanner down); authenticated writes fail open flagged `unscanned` and are swept hourly by `RescanUnscannedMessagesJob`
- Message size limits, recipient caps, protocol error budgets, credential redaction in debug traces

**Residual risks:**
- Port 25 accepts unauthenticated mail without requiring TLS (normal for MX; mitigated by sender auth + virus scan)
- `SMTP_SENDER_AUTH=0` disables SPF/DKIM/DMARC (warned at boot)
- `SMTP_DMARC_ENFORCE` only accepts literal `"1"` (misconfiguration warned)
- rspamd fail-open on authenticated submission (finding 4)

## Data Leak Paths Reviewed

| Path | Verdict |
|------|---------|
| HTTP responses / views | No `html_safe` in app views; mail in sandboxed iframe |
| Logs (production) | Emails/IPs in operational logs; params filtered |
| `auth_attempts` table | Usernames only, never passwords |
| `/metrics` | Aggregates only |
| `audit_events` | Admin actions, emails, IPs — intentional |
| Database | Full mail in `email_messages.raw` — expected; DKIM/SCRAM/TOTP encrypted |
| Backups | Full DB dump on local volume |
| Live connections UI | Peer IP, username, HELO — admin-only |
| Password reset email | Standard flow; no enumeration |
| Flash `generated_password` | Shown once in UI after create/reset |

---

## Recommendations (Priority Order)

1. **Add RBAC** if more than one person uses the admin UI (README roadmap).
2. **Encrypt and offsite database backups**; treat backup files as secret.
3. **Restrict `/metrics` at the network layer** and rotate `METRICS_TOKEN`.
4. **Switch published MTA-STS to `enforce`** (`MAIL_ON_RAILS_MTA_STS_MODE=enforce`) once TLS-RPT reports come back clean — the policy id self-bumps on the next DNS publish.
5. **Keep the Cloudflare token zone-scoped and rotated** (ops hygiene, finding 5).
