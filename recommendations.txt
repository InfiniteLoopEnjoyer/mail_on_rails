# Security Audit Report: mail_on_rails

**Scope:** Static review of the Rails 8.1 mail server codebase (web UI, SMTP/IMAP protocol servers, deployment config, CI).  
**Date:** August 7, 2026  
**Method:** Source review, configuration analysis, CI/security tooling inspection. Automated scanners (`brakeman`, `bundler-audit`) could not be run locally (Ruby not installed in this environment), but CI runs them on every PR and daily.

---

## Executive Summary

This is a **well-hardened** mail server for its size. It shows deliberate security engineering: multi-layer email XSS defenses, protocol-level auth throttling, virus/spam pipelines, encrypted secrets at rest, 2FA, and a strong CI security program (Brakeman, bundler-audit, importmap audit, Trivy).

The main gaps are **architectural** rather than obvious bugs:

1. **No authorization model** — every logged-in user is a full admin.
2. **Missing defense-in-depth on the web layer** — CSP and host authorization are disabled.
3. **Session lifecycle is permissive** — permanent cookies, no idle timeout, no IP binding.

None of these look like immediate remote-code-execution vulnerabilities, but they matter if this is exposed to multiple operators or the public internet.

## Findings by Severity

### High

#### 1. Flat admin model — no authorization / RBAC

**Location:** All authenticated controllers (`UsersController`, `DomainsController`, `EmailsController`, etc.)

Any authenticated `User` can:
- Create/delete other admin users and rotate their passwords
- Manage all email accounts, domains, DNS (Cloudflare publish)
- Ban IPs, change system settings, view audit logs and live SMTP/IMAP connections
- Send email as **any** hosted account (`EmailsController` comment confirms this is intentional)

**Risk:** Credential compromise of any single admin account = full system compromise. No separation between “mail user” and “operator.”

**Recommendation:**
- Introduce roles (e.g. `operator`, `mail_admin`, `read_only`)
- Scope email account access per user
- Protect destructive actions (domain delete, user delete, DNS publish) behind elevated role or confirmation step

---

#### 2. Host authorization disabled

**Location:** `config/environments/production.rb` (lines 87–94)

```87:94:config/environments/production.rb
  # Enable DNS rebinding protection and other `Host` header attacks.
  # config.hosts = [
  #   "example.com",     # Allow requests from example.com
  #   /.*\.example\.com/ # Allow requests from subdomains like `www.example.com`
  # ]
```

**Risk:** DNS rebinding and Host-header attacks. With `config.hosts` unset, Rails does not validate the `Host` header. Combined with the post-login redirect (finding #3), this can enable phishing or session confusion.

**Recommendation:** Set `config.hosts` from `MAIL_ON_RAILS_WEB_HOST` and any MTA-STS hostnames (e.g. `mta-sts.example.com`). Exclude `/up` for health checks as the commented template suggests.

---

#### 3. Post-login open redirect potential

**Location:** `app/controllers/concerns/authentication.rb`

```32:38:app/controllers/concerns/authentication.rb
    def request_authentication
      session[:return_to_after_authenticating] = request.url
      redirect_to new_session_path
    end

    def after_authentication_url
      session.delete(:return_to_after_authenticating) || root_url
```

**Risk:** `request.url` is stored verbatim and used in `redirect_to` after login. If Host header validation is absent (finding #2), a crafted request could store an attacker-controlled URL and redirect the user there post-authentication (open redirect). Even with host validation, storing full URLs is less safe than storing relative paths.

**Recommendation:**
- Validate `return_to` against an allowlist of same-origin paths
- Prefer `request.fullpath` over `request.url`
- Use Rails’ built-in `url_from` helper to reject external URLs

---

#### 4. Content Security Policy not enforced

**Location:** `config/initializers/content_security_policy.rb` (entire file commented out)

**Risk:** The admin UI has no CSP. Email content is well-defended (sanitizer + iframe sandbox), but a separate XSS in the admin UI (e.g. stored in a setting, future template bug) would have no browser-level mitigation.

**Recommendation:**
- Enable CSP in report-only mode first
- Add nonces for importmap/Stimulus scripts (the commented template already shows how)
- Tighten to enforcement once violations are resolved

---

### Medium

#### 5. Session cookies are permanent with no idle timeout

**Location:** `app/controllers/concerns/authentication.rb`

```61:65:app/controllers/concerns/authentication.rb
    def start_new_session_for(user)
      user.sessions.create!(user_agent: request.user_agent, ip_address: request.remote_ip).tap do |session|
        Current.session = session
        cookies.signed.permanent[:session_id] = { value: session.id, httponly: true, same_site: :lax }
```

**Risk:**
- `permanent` ≈ 20-year cookie lifetime
- No idle timeout or absolute expiry on `Session` records
- Sessions not re-validated against IP or User-Agent after creation (values are stored but not checked)

**Recommendation:**
- Use expiring cookies (e.g. 2 weeks) with sliding renewal
- Add `last_active_at` and expire idle sessions (e.g. 24h)
- Optionally invalidate sessions on IP/UA change (with care for mobile networks)

---

#### 6. Web login uses weaker throttling than mail protocols

**Location:** `SessionsController` vs `AuthThrottle`

Web login relies on Rails `rate_limit` (10 attempts / 3 min per IP, cache-backed). SMTP/IMAP use the durable `AuthThrottle` model with configurable IP and per-account blocks (`MAIL_ON_RAILS_AUTH_*` env vars).

**Risk:** Web brute-force attempts don’t share the same cross-connection, DB-backed throttle as mail auth. Cache eviction or multi-instance cache inconsistency could weaken protection.

**Recommendation:** Route web login failures through `AuthThrottle.record_failure` / `AuthThrottle.check`, matching mail protocol behavior.

---

#### 7. 2FA WebAuthn challenge endpoints lack rate limiting

**Location:** `app/controllers/two_factor/challenges_controller.rb`

TOTP verification is rate-limited; `webauthn_options` and `webauthn` are not.

**Risk:** Low practical impact (WebAuthn requires a physical key), but an attacker with a stolen password could probe the endpoint without throttling.

**Recommendation:** Add `rate_limit` to `webauthn_options` and `webauthn` actions, consistent with TOTP.

---

#### 8. No safeguard against deleting the last admin user

**Location:** `UsersController#destroy`

Any admin can delete any other user, including the last remaining account, with no minimum-user check.

**Risk:** Accidental or malicious lockout.

**Recommendation:** Block deletion when `User.count == 1`, or require at least one user with a specific role.

---

#### 9. Metrics endpoint information disclosure

**Location:** `app/controllers/metrics_controller.rb`

Properly gated (`METRICS_TOKEN` + `secure_compare`), but if the token leaks it exposes account counts, message counts, storage usage, auth failure tallies, and live connection counts.

**Recommendation:**
- Rotate `METRICS_TOKEN` periodically
- Restrict `/metrics` at the network layer (internal scrape only)
- Consider reducing metric cardinality in production

---

#### 10. Password reset flow generates a new password (not user-chosen)

**Location:** `app/controllers/passwords_controller.rb`

Reset does not let the user pick a password; it calls `regenerate_password!` and displays the generated password once.

**Risk:** Low security risk (actually strong entropy), but the reset link in email is high-value. Ensure token expiry is short (Rails `has_secure_password` reset tokens typically expire; tests confirm single-use).

**Recommendation:** Document token TTL explicitly; consider requiring 2FA before password reset for enrolled users.

## Email Security (Strong — Detailed)

The HTML mail rendering path is a model for defense in depth:

1. **Sanitization** — Tag/attribute allowlists, CSS scrubbing via Loofah, phishing link detection, remote image blocking by default
2. **Sandboxed iframe** — `sandbox="allow-popups allow-popups-to-escape-sandbox"` with no scripts
3. **Attachment gating** — Downloads blocked until virus scan is `clean`
4. **`.eml` download allowed without scan** — Reasonable (not executable in browser); documented in controller

```91:95:app/controllers/email_messages_controller.rb
  # Serves one MIME attachment as a download. The view only links attachments
  # on messages that pass attachments_downloadable?; enforce the same rule
  # here so a pasted URL can't fetch an unscanned or infected payload.
  def attachment
    head :forbidden and return unless @email_message.attachments_downloadable?
```

## Protocol / Infrastructure Security (Strong)

- SMTP: per-IP connection limits, auth lockout, tarpit rate limiter, send quotas, virus scan at DATA (451 when scanner down), DMARC enforcement option
- IMAP: SCRAM auth, APPEND size limits mirrored in web import
- Banned IPs: synced to listeners, self-ban protection, live connection kick on ban
- Docker: secrets excluded from image, non-root runtime

## Conclusion

**mail_on_rails** is above average for security among self-hosted mail projects. The mail pipeline (auth, throttling, virus/spam, XSS) is thoughtfully designed and tested. The biggest improvements are on the **web admin plane**: authorization, host validation, CSP, and session lifecycle.

I did not find evidence of hardcoded secrets, SQL injection, or obvious RCE paths in the reviewed code. The project’s CI security tooling is a strong foundation — keeping those scans green and addressing the P0/P1 items above would materially reduce risk.
